# 1. Executive verdict

## Verdict: **MUCH BETTER, BUT STILL NOT READY TO MERGE**

The latest commit fixes a large majority of the previously reported problems. The two most severe issues from the previous audit were substantially addressed:

- `BatchQueued` is now treated as active, preventing the simple second-click duplicate-Batch path.
- `BatchIngestionService` now performs an up-front `custom_id` validation pass before it mutates candidate/item state.
- Direct and Batch local-processing failures preserve raw-provider recovery authority.
- local recovery from `.raw.png` was implemented.
- Candidate PNG/hash checks were strengthened.
- API + Variants is explicitly blocked.
- editing the request-bound prompt/name now unloads the API image.
- Direct max-attempt semantics were corrected.
- Core coverage/mutation gates were strengthened.
- alpha-unknown warnings are now generated by preflight.
- output/error Batch file IDs are persisted.
- transient Direct failures receive `FailedRetryable`.
- the misleading “completed” status after a global Direct halt was fixed.

However, a thorough review of the actual implementation found **new and remaining release blockers**.

### Most important remaining issues

1. **P0 – Paid Direct output can still be lost and later re-billed if the very first raw-file persistence fails.**
2. **P0/P1 – Paid Batch output can be lost from the app’s recovery flow if local raw persistence fails; the remote result file is available, but the Batch is retired as terminal.**
3. **P1 – `_isSubmittingBatch` is not reset on several early Batch failure returns, leaving the application permanently stuck in “Batch submission active” state until restart.**
4. **P1 – End-to-end duplicate `custom_id` is still not globally fail-closed because the Core result parser collapses the duplicate before `BatchIngestionService` sees it.**
5. **P1 – `UncertainAfterInterruption` has no user-facing resolution/retry action. Some crash states therefore become dead ends.**
6. **P1 – `QueuedDirect` / `DirectRateLimited` are not recovered on restart and can remain stuck forever even though they were never sent to OpenAI.**
7. **P1 – local Batch candidate recovery writes the *local* batch ID into provenance instead of the OpenAI remote Batch ID.**
8. **P1 – Candidate verification still does not verify the full provenance identity bundle (CustomId, model, mode, provider resolution, raw hash, provider request ID, Batch ID).**
9. **P1 – a corrupt Ready candidate is marked `FailedPermanent` even when its valid raw provider output still exists, creating a local-recovery dead end.**
10. **P1 – API commits still fall back to the currently selected provider template if `OpenAI API.md` is unavailable, allowing contradictory provenance.**
11. **P2 – the intended `System.Security.Cryptography.ProtectedData` 10.0.11 package reference is currently in neither project.**
12. **P2 – strict DPAPI corruption handling now makes Settings effectively unrecoverable when `secrets.dat` is corrupt.**
13. **P2 – alpha-unknown warnings are computed but still not shown in the paid-action confirmation dialogs.**
14. **P2 – local candidate recovery does not run automatically on application startup/import; a recovered `Normalizing` item still looks “Generating” until the user presses a generation button.**
15. **P2 – no CI/status evidence exists for the audited HEAD.**

This commit should **not be reverted**. The best path is one more focused repair pass.

# N-001 — P0 — Direct provider output received, raw-file write fails, later remote re-generation is allowed

## Affected code

```text
MainForm.ApiGeneration.cs
GeneratedImageStagingService.cs
ApiPreflightService.cs
```

## Current sequence

Direct now correctly does:

```text
POST succeeds
↓
candidate bytes exist in memory
↓
calculate raw SHA
↓
SaveRawCandidate()
↓
persist Normalizing
↓
normalize
```

This is much better than before.

But consider:

```text
GenerateAsync succeeds
OpenAI has produced/billed the image
↓
SaveRawCandidate throws IOException
```

At this exact point:

```text
currentRecord.ProviderRawPath == null
```

The generic catch decides:

```text
providerOutputWasPersisted == false
```

An `IOException` is not a retryable OpenAI/network error.

Result:

```text
FailedPermanent / direct_failed
```

On the next Generate Now:

```text
FailedPermanent
+ no ProviderRawPath
→ preflight considers request eligible
→ user can generate again
```

The user is not told:

```text
“OpenAI already returned an image for this request.”
```

This can produce a second billable generation.

## Why this matters

The safest cost boundary is not “raw file was persisted”.

It is:

```text
the provider successfully returned image bytes
```

Once that happens, the app knows remote generation happened.

A local disk failure after that must not look like an ordinary provider failure.

## Required fix

Track provider-response receipt separately.

### Recommended record extension

Append optional fields to `GenerationItemRecord`:

```csharp
DateTimeOffset? ProviderOutputReceivedAtUtc = null,
bool ProviderOutputReceived = false
```

Appending optional parameters preserves JSON/backward compatibility reasonably well.

### Direct worker

Immediately after `GenerateAsync` returns:

```csharp
var providerOutputReceivedAtUtc =
    DateTimeOffset.UtcNow;

currentRecord =
    currentRecord with
    {
        ProviderOutputReceived =
            true,
        ProviderOutputReceivedAtUtc =
            providerOutputReceivedAtUtc,
        CandidateId =
            candidate.CandidateId,
        ProviderRequestId =
            candidate.ProviderRequestId,
        UpdatedAtUtc =
            providerOutputReceivedAtUtc
    };

// Important: persist before first local candidate-file write.
_generationJobStore.UpsertItem(
    currentRecord);
```

Then raw write.

If `SaveRawCandidate` fails:

```csharp
catch (Exception ex)
{
    if (currentRecord.ProviderOutputReceived
        && string.IsNullOrWhiteSpace(
            currentRecord.ProviderRawPath))
    {
        _generationJobStore.UpsertItem(
            currentRecord with
            {
                Status =
                    GenerationItemStatus.UncertainAfterInterruption,
                ErrorCode =
                    "provider_output_received_local_persist_failed",
                ErrorMessage =
                    "OpenAI returned an image, but the helper could not "
                    + "persist the provider output locally. A new remote "
                    + "generation may duplicate cost.",
                UpdatedAtUtc =
                    DateTimeOffset.UtcNow
            });

        return;
    }

    // existing classification...
}
```

## Optional local disk retry

Because the bytes are still in memory, the app can retry **the local write only** before giving up.

Example helper:

```csharp
private static async Task<string>
    SaveRawCandidateWithLocalRetryAsync(
        GeneratedImageStagingService staging,
        string manifestFingerprint,
        string requestKey,
        string candidateId,
        byte[] rawBytes,
        CancellationToken cancellationToken)
{
    Exception? last = null;

    for (var attempt = 1;
         attempt <= 3;
         attempt++)
    {
        cancellationToken.ThrowIfCancellationRequested();

        try
        {
            return staging.SaveRawCandidate(
                manifestFingerprint,
                requestKey,
                candidateId,
                rawBytes);
        }
        catch (IOException ex)
        {
            last = ex;

            if (attempt < 3)
            {
                await Task.Delay(
                    TimeSpan.FromMilliseconds(
                        100 * attempt),
                    cancellationToken)
                    .ConfigureAwait(false);
            }
        }
    }

    throw new IOException(
        "Provider output was received, but local raw staging failed.",
        last);
}
```

This retries **disk I/O only**, never the provider request.


# N-002 — P0/P1 — Batch result received, raw persistence fails, remote result becomes effectively abandoned

## Affected code

```text
BatchIngestionService.cs
MainForm.ApiGeneration.cs
```

## Current behavior

For a successful Batch item:

```text
remote Batch result file downloaded
↓
image bytes parsed successfully
↓
SaveRawCandidate(...)
```

If the raw write throws:

```csharp
Status = FailedPermanent
ErrorCode = "raw_save_error"
```

Then ingestion continues.

At the end the local Batch record is updated to:

```text
Status = status.Status
```

Normally:

```text
completed
```

`GenerationJobStore.GetActiveBatches()` excludes completed batches.

Therefore:

```text
remote output file still exists
but app no longer polls it
item has no raw local recovery file
item can later look eligible for new remote generation
```

The provider result could have been re-downloaded without paying for a new generation.

## Required design

Treat remote generation success + local raw persistence failure as a **local ingestion failure**, not a terminal provider failure.

### Add a local ingestion retry signal

Extend summary:

```csharp
public sealed record BatchIngestionSummary(
    int SuccessCount,
    int FailureCount,
    int HandledCount,
    IReadOnlyList<string> UnknownCustomIds,
    IReadOnlyList<string> DuplicateCustomIds,
    IReadOnlyList<string> MissingCustomIds,
    bool NeedsRemoteResultRedownload);
```

Track:

```csharp
var needsRemoteResultRedownload =
    false;
```

Raw-write failure:

```csharp
catch (Exception rawEx)
{
    needsRemoteResultRedownload =
        true;

    _jobStore.UpsertItem(
        currentRecord with
        {
            Status =
                GenerationItemStatus.FailedRetryable,
            ErrorCode =
                "batch_result_raw_persist_failed",
            ErrorMessage =
                "Provider Batch result was received, but local raw "
                + $"persistence failed: {rawEx.Message}",
            ProviderRequestId =
                output.ProviderRequestId,
            UpdatedAtUtc =
                DateTimeOffset.UtcNow
        });

    failCount++;
    continue;
}
```

At final Batch save:

```csharp
var localStatus =
    needsRemoteResultRedownload
        ? "IngestionFailed"
        : status.Status;

_jobStore.UpsertBatch(
    batch with
    {
        Status =
            localStatus,
        ProviderOutputFileId =
            status.OutputFileId,
        ProviderErrorFileId =
            status.ErrorFileId,
        CompletedCount =
            status.CompletedCount,
        FailedCount =
            status.FailedCount,
        ErrorMessage =
            needsRemoteResultRedownload
                ? "Remote Batch finished, but one or more result files "
                  + "could not be persisted locally. Result ingestion will retry."
                : batch.ErrorMessage,
        UpdatedAtUtc =
            DateTimeOffset.UtcNow,
        CompletedAtUtc =
            needsRemoteResultRedownload
                ? null
                : DateTimeOffset.UtcNow
    });
```

Because `IngestionFailed` is not one of the provider-terminal strings in `GetActiveBatches()`, it will be polled again.

## Make ingestion idempotent

On a retry, do not re-stage already Ready/Committed rows.

Before processing an output:

```csharp
var currentRecord =
    expected[output.CustomId];

handledCustomIds.Add(
    output.CustomId);

if (currentRecord.Status is
    GenerationItemStatus.Ready
    or GenerationItemStatus.Committed)
{
    successCount++;
    continue;
}
```

```text

Batch_ResultRawWriteFails_OutputFileIdPreserved
Batch_ResultRawWriteFails_NextPollRetriesDownload
Batch_ResultRawWriteFails_NeverCreatesNewRemoteBatch
Batch_Reingestion_AlreadyReadyItemIsIdempotentlySkipped
```

# N-003 — P1 REGRESSION — `_isSubmittingBatch` remains `true` after early Batch failures

## Affected code

```text
MainForm.ApiGeneration.cs
```

## Current structure

`SubmitBatchAsync()` starts with:

```csharp
_isSubmittingBatch = true;
ApplyRequestQueueState();
```

The flag is reset only in the `finally` around the **last** ProviderBatchId persistence block.

But these branches return earlier:

```text
UploadBatchInputFileAsync failure
ProviderInputFileId persistence failure
CreateBatchAsync failure
```

They call `return;` before reaching that `finally`.

Earlier code used to clear `_isSubmittingBatch` in these paths.

The newest repair removed those assignments but did not introduce an outer `finally`.

## Result

After one of these failures:

```text
_isSubmittingBatch == true
```

`ApplyRequestQueueState()` therefore keeps:

```text
Import disabled
Generate Now disabled
Queue Production Batch disabled
```

Closing the application also warns that a Batch submission is still in progress even though it already failed.

The user must restart the application.

## Best fix

Do not manually clear the flag in many catches.

Wrap the **whole** operation.

### Refactor

```csharp
private async Task SubmitBatchAsync(
    IReadOnlyList<AssetRequestItem> eligible,
    string apiKey)
{
    _isSubmittingBatch = true;
    SafeInvoke(ApplyRequestQueueState);

    try
    {
        await SubmitBatchCoreAsync(
            eligible,
            apiKey)
            .ConfigureAwait(false);
    }
    finally
    {
        _isSubmittingBatch = false;

        SafeInvoke(() =>
        {
            ApplyRequestQueueState();
            RefreshRequestQueueVisuals();
        });
    }
}
```

Move the current body after flag setup into:

```csharp
private async Task SubmitBatchCoreAsync(
    IReadOnlyList<AssetRequestItem> eligible,
    string apiKey)
```

All current internal `return;` calls are then safe.

For each failure boundary:

```text

```


Make the parser throw on duplicate immediately.

### Copy-ready change

Replace duplicate handling in `ParseLines`:

```csharp
if (!seenCustomIds.Add(

    throw new InvalidDataException(
```

Remove:

```text

post-processing loop that replaces results
```

Then change method signatures accordingly.

### Result

Any duplicate in:

```text
output file
error file
across output + error
```

throws before `DownloadBatchResultsAsync()` returns.

The polling path catches it as result-ingestion/download failure and no result-specific candidate mutation occurs.

# N-006 — P1 — unsent Direct queue states are stuck after restart

## Affected code

```text
GenerationJobStore.RecoverInterruptedJobsOnStartup()
```

Handled:

```text
DirectInFlight → Uncertain
```

Not handled:

```text
QueuedDirect
DirectRateLimited
```

These statuses are set before the provider HTTP request.

If the process dies while an item is waiting for the local limiter:

```text
restart
→ status still QueuedDirect / DirectRateLimited
→ no worker exists
→ preflight calls it active
→ item is permanently skipped
```

## Safe recovery

These states have not been provider-sent.

The worker writes:

```text
DirectInFlight
```

durably before calling the provider.

Therefore it is safe to convert:

```text
QueuedDirect → Pending
DirectRateLimited → Pending
```

on startup.

### Copy-ready code

Inside startup item loop:

```csharp
if (item.Status is
    GenerationItemStatus.QueuedDirect
    or GenerationItemStatus.DirectRateLimited)
{
    state.Items[i] =
        item with
        {
            Status =
                GenerationItemStatus.Pending,
            ErrorCode =
                null,
            ErrorMessage =
                "Queued Direct request was not in-flight when the previous process ended. "
                + "It was returned to Pending.",
            UpdatedAtUtc =
                DateTimeOffset.UtcNow
        };

    mutated = true;
}
else if (item.Status ==
         GenerationItemStatus.DirectInFlight)
{
    // existing Uncertain behavior
}
```

## Required tests

```text
Restart_QueuedDirect_BecomesPending
Restart_DirectRateLimited_BecomesPending
Restart_DirectInFlight_RemainsUncertain
```

```csharp
private bool HasRecoverableRawAuthority(
```

# 13. Final assessment

The latest repair commit is a substantial improvement over `f4f579b...`.

It correctly fixed many of the issues that were previously found and should be kept.

The main remaining architectural lesson is:

```text
The critical cost-safety boundary is not “raw file successfully written”.
It is “provider output definitely existed”.
```

Once an OpenAI response or Batch result has produced image bytes, every later local failure must be treated as a **local recovery problem**, not as an ordinary generation failure.

The other major remaining theme is:

```text
Uncertain must be safe,
but it must also be resolvable.
```

A state that correctly prevents automatic double billing but can never be consciously resolved by the user is still incomplete functionality.

One focused repair pass implementing the phases above should bring the branch much closer to merge readiness without redesigning the already-working API architecture or existing legacy workflows.
